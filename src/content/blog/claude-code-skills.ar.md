**باختصار:** مهارات Claude Code ملفات تعليمات قصيرة تمنح الوكيل عادات جيدة. أستعمل مهارات Matt Pocock للتخطيط (`/mattpocock-skills:wayfinder` و`/mattpocock-skills:grill-with-docs`)، وPonytail لإبقاء كل تغيير صغيراً، و`/ponytail-review` و`/mattpocock-skills:code-review` معاً قبل كل دمج.

وكيل البرمجة بالذكاء الاصطناعي، كما يأتي، سريع لكن بلا عادات. يبدأ البرمجة قبل أن يفهم ما تريد، ويكتب أكثر مما تحتاجه المهمة، ويراجع عمله بتساهل. **المهارات** (skills) تحل هذا. المهارة ملف Markdown قصير من التعليمات يحمّله الوكيل حين يكون مناسباً، أو حين تكتب اسمها كأمر يبدأ بـ `/`. إنه الفرق بين توظيف شخص موهوب وتوظيف شخص له منهج.

أستعمل مجموعتين كل يوم، في كل مشروع، مع Claude Code:

- **[Ponytail](https://github.com/dietrichgebert/ponytail)** من Dietrich Gebert: تجعل الوكيل يفكر مثل «المطوّر الخبير الكسول» (the lazy senior dev). يكتب فقط ما تحتاجه المهمة، ويعيد استعمال الموجود، ولا يتنازل أبداً عن التحقق من المدخلات أو معالجة الأخطاء أو الأمان أو إمكانية الوصول.
- **[مهارات Matt Pocock](https://github.com/mattpocock/skills)**: مهارات صغيرة قابلة للتركيب لـ«هندسة حقيقية، لا برمجة بالحدس». توحّد فهمك مع الوكيل قبل كتابة أي سطر، وتُبقي التحكم في يدك.

بعد بضعة أشهر، يظهر في سجلّي نمط واضح من ثلاث خطوات.

ملاحظة عن الأسماء قبل أن نبدأ: المجموعتان تُثبَّتان كمكوّنات إضافية (plugins) في Claude Code، وبعض أسماء الأوامر القصيرة تتعارض مع أوامر مدمجة في Claude Code. في هذه الحالة اكتب الاسم الكامل مع بادئة المكوّن الإضافي، مثل `/mattpocock-skills:code-review`. أكتب أدناه كل أوامر Matt Pocock باسمها الكامل، لتبقى صالحة حتى لو أضاف Claude Code أمراً بالاسم القصير نفسه.

## 1. التخطيط: الفهم قبل الكتابة

معظم النتائج السيئة للذكاء الاصطناعي سببها سوء فهم، لا كود سيئ. لذلك لا شيء يبدأ بالكود.

- **`/mattpocock-skills:wayfinder`** لكل عمل أكبر من جلسة واحدة. يحوّل فكرة غامضة إلى خريطة من *القرارات* على نظام التذاكر لديك (يُضبط مرة واحدة بـ `/mattpocock-skills:setup-matt-pocock-skills`، انظر أدناه)، ثم يحسمها واحدةً تلو الأخرى. ينتج قرارات لا كوداً: حين يتضح الطريق، تنتهي الخطة.
- **`/mattpocock-skills:grill-with-docs`** قبل كل مهمة. يطرح عليّ الوكيل أسئلة مرقّمة على دفعات، مع إجابته المقترحة لكل سؤال، حتى نتفق على ما سنبنيه. هذه الخطوة هي الأكثر توفيراً للوقت: عشر دقائق من الأسئلة بدل ساعات من إعادة العمل. وجزء «الوثائق» هو نمذجة المجال: أثناء النقاش يحتفظ الوكيل بملف `GLOSSARY.md` لمصطلحات المشروع، ويقترح سجل قرار قصيراً (ADR) للقرارات التي يصعب التراجع عنها، والمفاجئة، والناتجة عن مفاضلة حقيقية. الجلسة التالية، والوكيل التالي، يبدآن بنفس الكلمات ونفس القرارات. (`/mattpocock-skills:grill-me` يطرح الأسئلة دون الوثائق، لكل ما لا يتعلق بالبرمجة.)
- **`/mattpocock-skills:research`** حين يعتمد سؤال على حقائق: واجهة برمجية أو مكتبة أو مواصفة. وكيل يعمل في الخلفية يقرأ المصادر الأصلية (التوثيق الرسمي والكود المصدري) ويكتب ملاحظة Markdown مع المراجع، بينما أواصل عملي.

## 2. البناء: أصغر تغيير يعمل بالكامل

Ponytail مفعّلة دائماً: يحمّلها خطاف (hook، أي سكربت يشغّله Claude Code تلقائياً) في بداية كل جلسة، فلا أحتاج إلى تذكّرها. قبل كتابة أي كود، يتبع الوكيل قائمة مثل هذه (مبسّطة):

1. هل يجب أن يوجد هذا أصلاً؟
2. هل هو موجود في المشروع؟
3. هل هو في المكتبة القياسية أو المنصة؟
4. هل هو في تبعية لدينا أصلاً؟
5. هل يمكن كتابته في سطر واحد يفهمه القارئ من النظرة الأولى؟
6. بعد ذلك فقط: اكتب الحد الأدنى الذي يعمل.

مثال الـ README يلخّص الفكرة: لطلب منتقي تاريخ، كتب وكيل دون المهارة 335 سطراً؛ ومع Ponytail أعاد استعمال حقل الإدخال الموجود في المشروع مع منتقي التاريخ المدمج في المتصفح وكتب 10 أسطر. كود أقل يعني مراجعة أقل وصيانة أقل وأماكن أقل لاختباء الأخطاء.

ما يجعلها جديرة بالثقة هو قائمة ما **لا تحذفه أبداً**: التحقق من المدخلات عند حدود الثقة، ومعالجة الأخطاء التي تمنع فقدان البيانات، والأمان، وإمكانية الوصول. وفوق ذلك، يجب أن يرافق كل منطق جديد غير بسيط (شرط، أو حلقة، أو محلّل، أو مال، أو أمان) اختبارٌ صغير. كسول في الحل، لا في العمل.

عند وجود خلل، يستبدل **`/mattpocock-skills:diagnosing-bugs`** التخمين بمنهج: أولاً بناء فحص سريع يفشل على هذا الخلل بالذات، ثم تضييق نطاقه، واختبار الفرضيات، وإصلاح السبب الجذري، وإضافة اختبار يمنع عودته. ولسؤال تصميمي، يبني **`/mattpocock-skills:prototype`** نسخة مؤقتة للإجابة عنه قبل الالتزام.

## 3. المراجعة: مراجعان وزاويتان

هذان هما الأمران اللذان أستعملهما أكثر من غيرهما. كل تغيير يمر بهما معاً قبل دمجه:

- **`/ponytail-review`** يراجع مثل المطوّر الخبير الذي يُستدعى حين يتعطل شيء. يقرأ الكود الذي يلمسه التغيير، لا الفروقات (diff) وحدها، ويبحث عن الأخطاء وثغرات الأمان والسلوك تحت ضغط حقيقي والكود الخطِر دون اختبار والكود الذي يمكن حذفه. كل ملاحظة تشرح ما الخطأ، وكيف يُصلح، وماذا يحدث إن أُهمل.
- **`/mattpocock-skills:code-review`** يتحقق من أمرين آخرين جنباً إلى جنب: هل يتبع الكود قواعد المشروع نفسه، وهل يفعل فعلاً ما طلبته التذكرة؟ أما `/code-review` وحده فقد يشغّل المراجعة المدمجة في Claude Code، حسب التطبيق والإصدار؛ والاسم الكامل يشغّل دائماً مهارة Matt Pocock.

كل منهما يكتشف مشاكل مختلفة، لذلك أحتفظ بالاثنين. بعدها يكتب **`/mattpocock-skills:pr`** وصف طلب الدمج، مع أدلة قبل/بعد ومخاطر الدمج. ومن حين لآخر، يُجري **`/ponytail-audit`** نفس الفحوص على المستودع كاملاً ويرتّب ما يجب إصلاحه أولاً.

## كيف تثبّت Ponytail ومهارات Matt Pocock في Claude Code

داخل Claude Code، شغّل هذين الأمرين واحداً بعد الآخر:

```
/plugin marketplace add DietrichGebert/ponytail
```

```
/plugin install ponytail@ponytail
```

في الطرفية (terminal):

```bash
claude plugin install mattpocock-skills@claude-plugins-official
```

ثم، داخل Claude Code من جديد، شغّل `/mattpocock-skills:setup-matt-pocock-skills` مرة واحدة لكل مستودع: يسألك عن نظام التذاكر الذي تستعمله، والتصنيفات التي تفرز بها التذاكر، وأين تُحفظ الوثائق إن كان المستودع monorepo.

نصيحتي: لا تثبّت عشرين مهارة في اليوم الأول. ابدأ بـ **`/mattpocock-skills:grill-with-docs`** قبل كل مهمة و`/ponytail-review` قبل كل دمج. هذان الأمران وحدهما يغيّران جودة ما يسلّمه لك الوكيل. أضف الباقي حسب الحاجة. المجموعتان مفتوحتا المصدر وتُقرآن في دقائق: اقرأهما، وعدّلهما، واجعلهما ملكك.
